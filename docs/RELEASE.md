# RELEASE — релизная политика

Как проект выпускает релизы: версионирование, статусы и порядок проверок перед выпуском. Политика применяется с v0.3.

## Для чего и рамки

Проект ведёт один автор; внешней базы тестировщиков не предусматривается. Сигнал проверки — автоматические прогоны CI (GitHub Actions) и личная эксплуатация автора на боевом VPS. Лестницы «альфа → бета → стабильный» нет; статус определяется конкретными критериями ниже.

## Версионирование

- SemVer в фазе 0.x: минорный шаг (`v0.3 → v0.4`) может содержать ломающие изменения; патч (`v0.3 → v0.3.1`) — только исправления.
- Префикс `v` обязателен во всех тегах.

## Статусы и теги

Каждый релиз фиксируется аннотированным git-тегом по коммиту линии разработки `staging`. Релизных веток не заводят.

| Статус | Тег | Смысл |
|---|---|---|
| experimental | `vX.Y_experimental` (патчи: `vX.Y.Z_experimental`) | выпуск после зелёного CI; используется в реальной работе |
| stable | `vX.Y_stable` — вторым тегом на тот же коммит | выполнены критерии ниже |

- Перевод не меняет коммит: только тег, строку `Status` в CHANGELOG и флаг GitHub Release.
- Если следующий релиз вышел раньше, чем `vX.Y` набрал критерии stable, старый остаётся experimental — это штатный исход.
- Тег `v0.2_release` выпущен до этой политики в прежнем формате имени; не переименовывается.

### Критерии перевода experimental → stable (все три)

1. На релизном коммите — зелёный полный прогон CI: матрица дистрибутивов ubuntu 22.04 / 24.04 + debian 12, firewall-нога, тесты и линт CLI.
2. Релиз отработал на личном боевом VPS ≥14 дней без хотфиксов и регрессий.
3. На момент перевода по релизу нет открытых известных регрессий.

## Порядок выпуска

1. Работы накопились в `staging`.
2. `staging` пушится вручную; на head ждётся зелёный полный прогон GitHub Actions: workflow `molecule` (syntax, матрица дистрибутивов, firewall-нога) и workflow `python-client` (тесты и линт CLI). При падениях — фиксы отдельными коммитами и перезапуск, до зелёного.
3. Один коммит `docs: finalize vX.Y`: `docs/PLANNED.*`, обе половинки CHANGELOG, штампы `Version` / `Last updated` публичных документов, сводка в README и строка в таблицу статусов ниже.
4. Поверх finalize-коммита ставится аннотированный тег `vX.Y_experimental` и пушится (тоже руками).
5. Создаётся GitHub Release: заголовок — имя тега; тело — соответствующая секция CHANGELOG; experimental отмечается как pre-release, stable-перевод — как latest. Вложения релиза — только публичные файлы; конфиги с ключами в релиз не попадают.

Тег на непроверенный (без зелёного CI) коммит запрещён политикой.

## Статусы релизов

Короткий sha — проверенный код; прогоны видны в Actions-истории репозитория по этому коммиту. При переводе в stable статус в таблице обновляется (дата stable) finalize-коммитом следующего выпуска.

| Релиз | Проверенный код | Проверено CI | Статус |
|---|---|---|---|
| v0.3 | `cf98f0b` | матрица дистрибутивов (ubuntu 22.04 / 24.04, debian 12), firewall-нога, тесты и линт CLI — 2026-09-05 | `v0.3_experimental` |

## CHANGELOG

- Пара файлов в корне: `CHANGELOG.md` (RU) и `CHANGELOG.en.md` (EN); на релиз — секция `## [vX.Y] — YYYY-MM-DD` (Added / Changed / Fixed / Removed) со строкой `Status:`. Авто-bump версий нет.
- Заполняется из сообщений коммитов в момент выпуска; обе половины — одним коммитом, структура зеркальна.

## Релизный коммит

Его правила сводятся к шагу 3 «Порядка выпуска»: `docs/PLANNED.*` (переработка «что дальше» под новую версию), штампы публичных документов, сводка README, обе половинки CHANGELOG. Настоящий документ (`docs/RELEASE.*`) до момента выпуска релиза правится обычными коммитами.
