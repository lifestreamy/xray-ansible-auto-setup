# RELEASE — релизная политика и приёмка релизов

Здесь зафиксировано, как проект выпускает релизы: версионирование, статусы, порядок приёмки тестов перед выпуском и место, где живут записи о пройденных проверках. Политика применяется, начиная с v0.3.

## Для чего и рамки

Проект ведётся одним человеком, внешней базы тестировщиков нет. Поэтому честный сигнал «проверено» — только автоматизированные прогоны (локальные тесты и CI на GitHub Actions) плюс личный приём автора на боевом сервере. Лестницы «альфа → бета → стабильный по внешним отзывам» не существует. Статус релиза определяется конкретными критериями ниже, а не ожиданиями тестов, которых в этом проекте не будет.

## Версионирование

- SemVer в фазе 0.x: минорный шаг (`v0.3 → v0.4`) может содержать ломающие изменения; патч (`v0.3 → v0.3.1`) — только багфиксы.
- Префикс `v` обязателен во всех тегах.

## Статусы и теги

Каждый релиз фиксируется аннотированным git-тегом по хэшу коммита в линии разработки `staging`. Релизные ветки не заводятся.

| Статус | Тег | Смысл |
|---|---|---|
| experimental | `vX.Y_experimental` (патчи: `vX.Y.Z_experimental`) | выпуск сразу после приёмки тестов; используется в реальной работе |
| stable | `vX.Y_stable` — вторым тегом на тот же коммит | выполнены все критерии перевода (ниже) |

- При переводе коммит релиза не меняется: меняется только статус — новый тег, строка статуса в CHANGELOG и флаг GitHub Release.
- Если следующий релиз вышел раньше, чем `vX.Y` набрал критерии stable, старый релиз остаётся experimental навсегда — это штатный исход.
- Историческая справка: тег `v0.2_release` выпущен до этой политики в прежнем формате имени; не переименовывается.

### Критерии перевода experimental → stable (все три обязательны)

1. На релизном коммите — зелёный полный прогон CI (матрица дистрибутивов ubuntu 22.04 / 24.04 + debian 12 и отдельная проверка firewall-задачи).
2. Релиз отработал на личном боевом VPS не менее 14 дней без хотфиксов и регрессий.
3. На момент перевода по релизу нет открытых известных регрессий.

## Процедура приёмки перед выпуском

Релиз `vX.Y` выпускается строго в таком порядке:

1. Задачи накоплены в линии разработки `staging`.
2. `staging` пушится в GitHub вручную (только человеком; автоматизация push не предусмотрена).
3. Ожидается зелёный прогон GitHub Actions на верхнем коммите: matrix-джобы по дистрибутивам плюс firewall-нога. При падениях — фиксы отдельными коммитами и перезапуск, до зелёного результата.
4. Фиксация: отдельный коммит добавляет в секцию «Приёмка релизов» (ниже) запись о пройденных прогонах — ссылки, матрица, даты. Такой коммит не трогает ничего, кроме этой секции (при первом применении — плюс навигационную строку в README).
5. Только после этого ставится аннотированный тег `vX.Y_experimental` на тот же коммит и пушится следом.
6. Создаётся GitHub Release: заголовок — имя тега; тело — соответствующая секция `CHANGELOG` плюс ссылка на запись приёмки ниже; experimental-релиз отмечается как pre-release, stable-перевод — как latest. Вложения релиза — только публичные файлы. Конфиги с ключами в релиз не попадают.

Тег на непроверенный коммит (без зелёного CI и без фиксации прогонов) политикой запрещён.

## Приёмка релизов

Формат записи на каждый релиз (новые — сверху):

```text
### vX.Y — приёмка

- Дата: YYYY-MM-DD
- GitHub Actions: <ссылки на прогоны> — матрица ubuntu2204/ubuntu2404/debian12 + firewall-нога, зелёный
- Локальные прогоны: scripts/test/local_test.py --runtime native (full cycle), <окружение>, дата — зелёный
- Личная приёмка: <VPS>, дата
- Вердикт: experimental
```

Первые записи появятся с релизом v0.3 — их добавляет процедура выпуска по формату выше.

## CHANGELOG

- Ведётся парой файлов в корне репозитория: [`CHANGELOG.md`](../CHANGELOG.md) (RU) и [`CHANGELOG.en.md`](../CHANGELOG.en.md) (EN).
- На каждый релиз — секция `## [vX.Y] — YYYY-MM-DD`: категории Added / Changed / Fixed / Removed, строка `Status:` (экспериментальный / с даты `stable`), строка-указатель на запись приёмки в этом документе.
- Заполняется из сообщений коммитов только в момент выпуска; новые версии сверху; авто-bump версий нет.
- Обе половины пары обновляются одним и тем же коммитом, структура зеркальна — это защита от расхождения RU/EN.

## Релизный коммит

Выпуск версии сопровождается отдельным релизным коммитом, который обновляет:

- `docs/PLANNED.md` и `docs/PLANNED.en.md` — переработка «что дальше» под новую версию (эти два файла вне релизного коммита не правятся);
- штампы `Version` / `Last updated` всех публичных документов;
- `README.md` / `README.en.md` — сводка «новое с прошлой версии»;
- обе половинки `CHANGELOG`.

Настоящий документ (`docs/RELEASE.*`) и `CHANGELOG` до момента выпуска релиза правятся обычными коммитами.
