# RELEASE — релизная политика

Как проект выпускает релизы: версионирование, статусы и порядок проверок перед выпуском. Политика применяется с v0.3.

## Для чего и рамки

Вклад в проект приветствуется (issues и pull requests на GitHub). Сигналы качества выпусков — автоматические прогоны CI (GitHub Actions), эксплуатация на боевом VPS и отчёты пользователей по stable-выпускам (issues на GitHub). Лестницы «альфа → бета → стабильный» нет; статус определяется конкретными критериями ниже.

## Версионирование

- Версия — трёхзначная `vX.Y.Z` (начиная с v0.4.0; старые двузначные теги — история, не переименовываются).
- SemVer в фазе 0.x: минор (`v0.3 → v0.4.0`) — существенные изменения, включая ломающие (например, смена дефолта CLI-флага); патч (`v0.4.0 → v0.4.1`) — исправления, удаления experimental-возможностей и небольшие переименования (с записью в CHANGELOG).
- Префикс `v` обязателен во всех тегах.

## Статусы и теги

Каждый релиз фиксируется аннотированным git-тегом по коммиту линии разработки `staging`. Релизных веток не заводят.

Статусы — явным списком:

- Код в `staging` без тега — **не релиз и без статуса**; он может никогда не стать релизом.
- **experimental** — выпущенный pre-release: тег `vX.Y.Z_experimental` + GitHub Release с флагом pre-release, переданный в ручную эксплуатацию — используется на боевом VPS, набирает критерии перевода. Статус experimental присваивается только после публикации pre-release.
- **stable** — выполнены все критерии перевода (см. ниже); второй тег `vX.Y.Z_stable` на тот же коммит + флаг latest у GitHub Release.

- Перевод не меняет коммит: только тег, строку `Status` в CHANGELOG и флаг GitHub Release.
- Если следующий релиз вышел раньше, чем `vX.Y.Z` набрал критерии stable, старый остаётся experimental — это штатный исход.
- Теги `v0.2_release` и `v0.3_experimental` выпущены в прежнем двузначном формате — история, не переименовываются.

### Критерии перевода experimental → stable (все четыре)

1. На релизном коммите — зелёный полный прогон CI: матрица дистрибутивов ubuntu 22.04 / 24.04 + debian 12, firewall-нога, тесты и линт CLI.
2. CI максимально покрывает клиентские сценарии: python-клиент + bash- и PowerShell-обёртки × раннеры ubuntu / windows / macos; недостающее покрытие достраивается до перевода.
3. Владелец вручную прокликал все сценарии использования на реальном VPS по шпаргалке тестирования (`docs/TEST-LOCAL.md`, `docs/TEST-VPS.md`): деплой двумя способами, ротация, юзабилити клиентов (отзывчивость, переводы, понятность текстов), реальная работа VPN.
4. На момент перевода по релизу нет открытых известных регрессий и хотфиксов.

Календарная выдержка не является критерием (решение 2026-09-09): деплой либо падает сразу, либо работает; основной риск — в процессе развёртывания и генерации конфигов, его и покрывают проверки выше.

## Порядок выпуска

Релиз выпускается один на версию — после выполнения всего запланированного скоупа версии; промежуточные pre-release на частично готовую работу не выпускаются (решение 2026-09-09).

1. Скоуп версии (волны работ) выполнен в `staging`; каждая волна пушится и проверяется зелёным CI до перехода к следующей.
2. `staging` пушится вручную; на head ждётся зелёный полный прогон GitHub Actions: workflow `molecule` (syntax, матрица дистрибутивов, firewall-нога) и workflow `python-client` (тесты и линт CLI). При падениях — фиксы отдельными коммитами и перезапуск, до зелёного.
3. Один коммит `docs: finalize vX.Y.Z`: `docs/PLANNED.*`, обе половинки CHANGELOG, штампы `Version` / `Last updated` публичных документов, сводка в README, строка в таблицу статусов ниже и bump версии пакета python-client (`pyproject.toml`, `src/xrayvpn/__init__.py`, `uv.lock`) до версии релиза.
4. Владелец выполняет успешное ручное развёртывание релизного содержимого на реальном VPS — релиз публикуется только после этого.
5. PR из `staging` в `main` мержится методом **Create a merge commit** (web-rebase запрещён — пересоздаёт коммиты, срезает подписи и даты).
6. На merge-node ставится подписанный аннотированный тег `vX.Y.Z_experimental` и пушится (руками).
7. Создаётся GitHub Release: заголовок — имя тега; тело — соответствующая секция CHANGELOG; experimental отмечается как pre-release, stable-перевод — как latest. Вложения релиза — только публичные файлы; конфиги с ключами в релиз не попадают.

Тег на непроверенный (без зелёного CI) коммит запрещён политикой.

## CHANGELOG

- Пара файлов в корне: `CHANGELOG.md` (RU) и `CHANGELOG.en.md` (EN); на релиз — секция `## [vX.Y.Z] — YYYY-MM-DD` (Added / Changed / Fixed / Removed) со строкой `Status:`. Авто-bump версий нет.
- Заполняется из сообщений коммитов в момент выпуска; обе половины — одним коммитом, структура зеркальна.

## Релизный коммит

Его правила сводятся к шагу 3 «Порядка выпуска»: `docs/PLANNED.*` (переработка «что дальше» под новую версию), штампы публичных документов, сводка README, обе половинки CHANGELOG. Настоящий документ (`docs/RELEASE.md`) до момента выпуска релиза правится обычными коммитами.

Версия пакета python-client всегда равна версии релиза: finalize-коммит бампит `pyproject.toml` и `src/xrayvpn/__init__.py` (и обновляет `uv.lock`) до `vX.Y.Z`; `xrayvpn --version` обязан совпадать с тегом. Рассинхрон ловит тест `tests/test_smoke.py`.
