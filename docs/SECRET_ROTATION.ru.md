# Ротация секретов — runbook

Runbook для ротации учётных данных после компрометации или по расписанию. Заменяйте `<VPS_IP>` и другие плейсхолдеры только при реальной ротации на живом VPS.

Этот документ описывает фактическое поведение работающей роли Ansible. Если что-то здесь не совпадает с тем, что отработал playbook — открывайте issue: runbook — источник правды для операции, роль — источник правды для кода.

## 1. Обычный повторный запуск

По умолчанию повторный прогон playbook **ничего не ротирует**. Роль сохраняет существующую идентичность и учётные данные.

- REALITY `private_key`, `public_key`, `short_id` и `client_uuids` хранятся в `/root/xray-config/reality-state.json` (режим `0600`).
- Учётные данные WARP хранятся в `wgcf-account.toml` и `wgcf-profile.conf` в `/root/xray-config/`.
- Шаблон `xray_config.json` регенерируется при каждом запуске из сохранённого состояния и текущих параметров.

То есть если между двумя прогонами вы ничего не меняли, второй прогон выдаст идентичные клиентские конфиги и ту же идентичность Xray-сервера.

## 2. Ротация идентичности REALITY (полный rekey)

Используйте, когда ключи или short ID REALITY были скомпрометированы, либо по плановому графику.

У роли один переключатель:

```yaml
xray_reality_rotate: true
```

Передайте его через `group_vars/all.yml` для разового запуска, либо через `-e xray_reality_rotate=true` в командной строке:

```bash
ansible-playbook -i inventory.yml deploy.yml -e xray_reality_rotate=true
```

Что происходит при включённом тумблере:

1. Текущий `reality-state.json` бэкапится в `reality-state.json.bak-YYYY-MM-DD-HH:MM:SS` в той же папке.
2. Файл текущего состояния удаляется.
3. Генерируется новая X25519-пара ключей, новый случайный short ID, новые клиентские UUID.
4. Записывается новый `reality-state.json`.
5. Сервис Xray перезапускается с обновлённым `config.json`.

После прогона:

- Проверьте новые клиентские конфиги в `/root/vpn-configs/` на VPS, либо скачайте их локально (`downloaded-clients/`).
- Раздайте новые конфиги клиентам.
- Верните `xray_reality_rotate` в `false` в `group_vars/all.yml`. Если оставить `true`, идентичность будет ротироваться при каждом запуске — почти наверняка вы этого не хотите.

## 3. Изменения только числа клиентов

`num_clients` задаёт, сколько клиентских конфигов выгружается. При персистентном состоянии поведение добавления:

- Увеличили `num_clients` → в `reality-state.json` добавляются новые UUID, экспортируются новые клиентские конфиги.
- Уменьшили `num_clients` → уже существующие UUID в `reality-state.json` сохраняются, просто экспортируется меньше конфигов.
- Увеличили обратно → ранее сохранённые UUID снова используются.

Если нужна настоящая ротация (регенерация) клиентских UUID — делайте полную ротацию через раздел 2.

## 4. Ротация учётных данных WARP

Учётные данные WARP получаются через `wgcf` и хранятся в двух файлах на VPS:

- `/root/xray-config/wgcf-account.toml`
- `/root/xray-config/wgcf-profile.conf`

Важно: `wgcf-identity.json` в этой конфигурации не используется. В старых версиях runbook этот файл упоминался — игнорируйте те упоминания.

Чтобы выполнить ротацию:

1. Зайдите на VPS по SSH: `ssh root@<VPS_IP>`.
2. Удалите оба файла выше.
3. Перезапустите playbook. Роль вызовет `wgcf register` и `wgcf generate` заново, и WARP outbound в `xray_config.json` подхватит новые учётные данные.

Проверять WARP-маршрутизацию лучше снаружи VPS — реальным клиентом, подключённым через новый WARP outbound. Например, откройте `https://ifconfig.io` или `https://cloudflare.com/cdn-cgi/trace` с активным VPN. Не полагайтесь на `curl` из контейнера Xray.

## 5. Восстановление

Роль и так делает бэкап с меткой времени перед ротацией, поэтому неуспешная ротация редко бывает деструктивной. Типичное восстановление:

1. Зайдите на VPS по SSH: `ssh root@<VPS_IP>`.
2. Посмотрите бэкапы: `ls -la /root/xray-config/reality-state.json.bak-*`.
3. Если хотите откатиться на предыдущее состояние:
   ```bash
   cp /root/xray-config/reality-state.json.bak-YYYY-MM-DD-HH:MM:SS \
      /root/xray-config/reality-state.json
   chown root:root /root/xray-config/reality-state.json
   chmod 0600 /root/xray-config/reality-state.json
   ```
4. Убедитесь, что в `group_vars/all.yml` стоит `xray_reality_rotate: false`.
5. Перезапустите playbook. Роль подхватит восстановленное состояние и перегенерирует `config.json` и клиентские конфиги под него.

Держите хотя бы последний бэкап, пока не проверите новую ротацию end-to-end.

## 6. Проверка после развёртывания

После успешной ротации (или любого прогона):

- `docker inspect xray --format '{{ .Config.Image }}'` — должно вернуть `teddysun/xray:26.6.27` (или текущее значение `xray_docker_image`).
- `journalctl -u xray --no-pager -n 30` — не должно быть ошибок REALITY-хендшейка.
- Xray-порт (`xray_port`, по умолчанию `443`) должен слушать на VPS: `nc -zv <VPS_IP> 443`.
- Подключитесь хотя бы одним реальным клиентом (Clash Verge / FlClash / Amnezia) и проверьте, что трафик идёт через него.

Встроенные проверки роли — non-fatal и покрывают только закреплённый образ, слушающий порт и очевидные ошибки журнала. Они не заменяют ручную проверку выше.
